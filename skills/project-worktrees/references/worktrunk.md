# Worktrunk and optional bootstrap

Contents: [macOS and zsh](#macos-and-zsh) · [Configuration](#configuration-scope) ·
[Verification](#effective-verification) · [Bootstrap](#optional-bootstrap) · [Sources](#sources)

Verified against **0.82.0** on 2026-11-18. The helper needs **0.81.0+**, which introduced
the non-mutating expected-path function. Worktrunk requires Git 2.43+; the standalone
migration runner supports Git 2.36+. Python 3.11+ supplies TOML parsing with no packages.

## macOS and zsh

```sh
brew install git python worktrunk
wt config shell install zsh
```

Use existing sufficient installations. Open a new terminal, then run `wt --version`,
`type wt`, and `wt config show`. `echo "$SHELL"` shows the configured login shell, not
necessarily the currently executing interpreter. The wrappers use portable `/bin/sh`.

## Configuration scope

| File | Responsibility |
| --- | --- |
| User config, normally `~/.config/worktrunk/config.toml` | Personal worktree paths and per-project overrides. |
| Repository `.config/wt.toml` | Shared hooks and other supported project settings. |

After migration, discover `user.path` and `project.identifier` with:

```sh
wt -C /absolute/project/main config show --format=json
```

Do not publish full configuration output; command settings can contain sensitive arguments.
For a GitHub project, the entry is:

```toml
[projects."github.com/owner/project"]
worktree-path = "{{ repo_path }}/../worktrees/{{ branch | sanitize }}"
```

`repo_path` stays anchored at the conventional primary checkout from any linked checkout.
`repo` would be `main` in this layout. The identifier normally follows the remote, so the
preference applies to other local clones of that project. Without a remote, it can be
path-derived: obtain it after moving.

`configure_worktrunk.py` previews by default. `--apply` appends a new project table,
validates candidate TOML, preserves original bytes as a prefix, and saves a private backup
of an existing file. Matching entries are no-ops. Conflicting project entries, symlink or
hardlink configurations, and TOML that cannot be extended require a deliberate scoped edit
preserving other settings, followed by `--check`. Do not replace the entire user config.

Do not edit this file concurrently. The helper takes its own exclusive lock and rechecks
before replacement, but unrelated editors do not honor that lock. If post-save verification
fails, the edit and backup remain for diagnosis. Report this separately from Git migration.

## Effective verification

```sh
wt -C /absolute/project/main step eval \
  '{{ expected_worktree_path_of_branch("feature/example") }}' --format=json
```

Use an unused non-default probe name; the default branch normally resolves to the primary
checkout. The helper checks primary and linked contexts, without creating a branch, then
compares Git registrations with Worktrunk's list. It disables external optional collection:

```sh
wt -C /absolute/project/main \
  --config-set list.full=false --config-set list.summary=false \
  --config-set list.branches=false --config-set list.remotes=false \
  --config-set list.json-schema=2 list --format=json
```

Schema 2 uses `items[].worktree.path`. Listing may update caches under `.git/wt`; do not
claim every Git metadata byte remains unchanged. No bootstrap hooks, branches, LLM
summaries, or CI collection are requested by this verifier.

The helper checks active Git clean/process filters in every registered checkout before
invoking Worktrunk and refuses executable filters. It propagates temporary Git overrides
disabling filesystem-monitor and Git hooks into Worktrunk's child processes, preserving
existing command-scoped Git settings. It does not rewrite stored Git safety settings.

Worktrunk may discover an uncached default branch with `git ls-remote` when no local
remote-HEAD ref is available. Disabling CI/LLM collection is not an unconditional offline
guarantee. The migration engine itself uses only local Git operations.

Do not use `wt step relocate` as this skill's engine: its primary-checkout behavior can
switch branches and leave untracked/ignored files behind. `wt switch` has no documented
`--dry-run`; use `step eval`. `wt config update` migrates deprecated settings, not arbitrary keys.

## Optional bootstrap

Leave it disabled by default. If requested, inspect existing toolchain pins, lockfiles,
setup tasks, environment handling, and `.config/wt.toml`. The disabled `assets/` examples
are starting points; do not overwrite existing project files. An enabled hook can be:

```toml
[pre-start]
bootstrap = "sh scripts/bootstrap-worktree"
```

In 0.82, `pre-start` runs after the new checkout exists, blocking later startup and
`--execute`. Review the installed lifecycle and hook approvals before enabling it.
Migration itself never invokes the hook. Use the project's reviewed locked-install task;
do not guess a full bootstrap from one file extension.

Use existing secret-loading conventions, keep secrets out of tracked files/logs, and do
not auto-copy every ignored file or share mutable dependency directories across agents.
Where needed, isolate ports, database/schema names, and Compose project names. Verify port
availability. Since `repo` is always `main`, use the full project path or another stable
identity to distinguish projects. Hash-derived ports can collide and do not reserve ports.
